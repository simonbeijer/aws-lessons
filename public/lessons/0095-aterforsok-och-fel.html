Vad händer när handlern kastar?

Kort sagt Förra lektionen slutade med att ett kast skickar tillbaka meddelandet till kön. Här är vad som händer sedan: meddelandet får nya försök, och den som anropade API:et (Application Programming Interface) märker ingenting. Därför ska koden bara kasta när ett nytt försök kan hjälpa.

Vad händer efter ett kast?

Klienten har redan fått sitt svar. API:et svarade 201 när SendMessage lagt meddelandet på kön (lektion 91), innan någon funktion körts. Till skillnad från ett kast bakom API:et (lektion 83) når felet aldrig klienten. Det syns bara i loggen.

Kastar handlern tas inget bort, och meddelandet blir synligt igen när visibility timeout gått ut (lektion 88). Receive count går upp vid varje hämtning, så loggen kan visa attempt 1, 2, 3. Efter tre misslyckade körningar flyttas meddelandet till dödbrevskön.

Kasta eller hoppa över?

Ett kast hjälper bara om ett nytt försök kan lyckas. Ett tillfälligt fel går över av sig självt, som throttling (lektion 84) eller ett 5xx-fel från tjänsten, och ska kastas. Ett sådant fel går att simulera genom att kasta med flit, till exempel när kundens namn börjar med FEL.

Ett permanent fel ger samma svar varje gång. Är kunden borttagen ger UpdateItem med villkoret attribute_exists(id) felet ConditionalCheckFailedException (lektion 79), och inga försök får kunden tillbaka. Kastas det felet också hamnar meddelandet i dödbrevskön i onödan. Därför fångar koden just det felet, skriver en varning i loggen med console.warn och går vidare till nästa post med continue. Returnerar handlern utan fel tar triggern bort meddelandet. Så ser det ut:

try {
  await db.send(new UpdateCommand({ /* … */ }));
} catch (err) {
  if (err.name === "ConditionalCheckFailedException") {
    console.warn("Kunden finns inte");
    continue;
  }
  throw err; // allt annat: tillbaka till kön
}

Quiz

1. Handlern kastar för ett meddelande tre gånger i rad. Vad har klienten som skapade kunden fått?

2. Kunden som meddelandet gäller är borttagen och UpdateItem ger ConditionalCheckFailedException. Vad ska handlern göra?

3. Kunden heter FEL Testsson, så handlern kastar varje gång. Var är meddelandet efter tredje försöket?

Sammanfattning

  • Ett kast tar inte bort meddelandet. Det kommer tillbaka efter visibility timeout, och efter tre misslyckade körningar (maxReceiveCount 3) hamnar det i dödbrevskön.
  • Klienten har redan fått 201. Felet syns bara i loggen och i dödbrevskön.
  • Tillfälligt fel (går över): kasta. Permanent fel (kunden finns inte, ConditionalCheckFailedException): console.warn och continue, så att triggern tar bort meddelandet.

Källor

Huvudkällor: AWS: felhantering för SQS i Lambda och AWS: Lambda med SQS. Dessutom AWS: SetQueueAttributes och AWS: felhantering i DynamoDB. Att err.name är ConditionalCheckFailedException i AWS SDK (software development kit) är hämtat från kursen, inte kontrollerat i AWS dokumentation. Vilket receive count dödbrevskön visar efter flytten är inte bekräftat: kursen säger 3, men AWS regel flyttar meddelandet vid fjärde hämtningen (lektion 89).
