Hur lägger API:et ett meddelande i kön?

Kort sagt Hittills har lektionerna handlat om kön och vad som händer med ett meddelande där. Nu är det producentens tur: API:et (Application Programming Interface) lägger själv meddelandet i kön när en kund skapas, med anropet SendMessage. Koden är kort, men rollen måste få skicka och meddelandet bära rätt uppgifter.

Hur skickar koden?

Koden lägger ett meddelande på SQS-kön (Simple Queue Service) med AWS SDK (Software Development Kit, som i lektion 81) och kommandot SendMessageCommand. Det behöver två saker: QueueUrl, köns adress, och MessageBody, meddelandet. Kroppen är en sträng, så ett objekt görs först om till JSON (JavaScript Object Notation) med JSON.stringify (lektion 83). Adressen läses från miljövariabeln QUEUE_URL, så koden kan byta kö utan att ändras.

import { SQSClient, SendMessageCommand } from "@aws-sdk/client-sqs";

const client = new SQSClient({});

await client.send(new SendMessageCommand({
  QueueUrl: process.env.QUEUE_URL,
  MessageBody: JSON.stringify({ id: "c-1042" })
}));

Rollen som funktionen kör med (execution role) måste också få skicka. Den får sqs:SendMessage på just den här kön, med köns ARN (Amazon Resource Name) som Resource. Det är minsta möjliga behörighet: en bugg kan skicka meddelanden, men inte hämta eller radera dem.

Vad ska meddelandet bära?

Bara det konsumenten behöver: vad som hänt, kundens id, namnet och tiden, som i JSON-exemplet i lektion 87. Hela kunden skickas inte, för där kan det finnas sådant konsumenten inte ska se, till exempel ett lösenord. Med id:t kan konsumenten hämta resten ur tabellen.

Meddelandet är också en kopia av uppgifterna från när det skickades. Ändras namnet i tabellen medan meddelandet väntar, står det gamla kvar i meddelandet. Det gäller också efter en redrive: rättas namnet i tabellen, kommer meddelandet tillbaka med det gamla och kan misslyckas igen. Därför hämtar konsumenten färska uppgifter ur tabellen när de kan ha ändrats.

Sammanfattning

  • SendMessageCommand med QueueUrl och MessageBody (en sträng) lägger ett meddelande på kön.
  • Rollen får bara sqs:SendMessage på en kö, med köns ARN som Resource.
  • Meddelandet bär bara det konsumenten behöver, och är en kopia som kan bli inaktuell.

Källor

Huvudkälla: AWS: SendMessage. Dessutom SendMessage med SDK for JavaScript och SQS API permissions. Att meddelandet ska vara smalt och kan bli inaktuellt är kursens designval, inte en AWS-regel: AWS visar både händelser med data och händelser med bara ett id (Event-driven architecture).
